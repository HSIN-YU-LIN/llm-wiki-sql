01 — 問題

同一個問題，兩種速度

這兩行 SQL 要的東西一模一樣，但快慢可以差幾千倍。

SELECT name FROM employee WHERE dept_id = 1;

資料庫可以從頭到尾讀完整張表，一列一列比對；也可以直接跳到第 1 號部門那一段。

你寫的 SQL 沒有指定用哪一種。

那麼，是誰決定的？

這份簡報從「什麼是一張表」開始，一路走到你能自己看出資料庫選了哪一條路。

02 — 基礎

先認識一張表

關聯式資料庫把資料存成表（table）。欄（column）定義結構，列（row）是一筆筆資料。

CREATE TABLE employee (id, name, dept_id, salary);
CREATE TABLE department (id, name);

整份簡報都用這兩張表。employee.dept_id 對應到 department.id，這個對應關係就是等一下 JOIN 的依據。

idnamedept_idsalary
1陳怡君162000
2林志明158000
3王美玲251000
4張家豪NULL47000

注意第 4 列的 NULL——張家豪還沒分配部門。這個值等一下會惹出麻煩。

03 — 基礎

問第一個問題

一個查詢只需要兩個動作：挑欄位和挑列。

SELECT name, salary     -- 挑欄位
FROM   employee         -- 從哪張表
WHERE  dept_id = 1;     -- 挑列

執行結果

陳怡君 | 62000
林志明 | 58000

數學上的對應

SELECT 是投影（挑欄）
WHERE 是選擇（挑列）
SQL 本質上是關係代數的語法糖。

就這樣。接下來所有複雜的東西，都是在這兩個動作上加料。

04 — JOIN

把兩張表接起來

JOIN 依條件把兩張表的列配對。差別只在配不到的列怎麼辦。

INNER JOIN — 配不到就丟掉

SELECT e.name, d.name
FROM employee e
INNER JOIN department d
  ON e.dept_id = d.id;
陳怡君 | 工程
林志明 | 工程
王美玲 | 行銷

張家豪不見了（他的 dept_id 是 NULL）

LEFT JOIN — 左表每列都留

SELECT e.name, d.name
FROM employee e
LEFT JOIN department d
  ON e.dept_id = d.id;
陳怡君 | 工程
林志明 | 工程
王美玲 | 行銷
張家豪 | NULL

配不到的用 NULL 補齊

RIGHT JOIN 反過來保留右表；FULL OUTER JOIN 兩邊都保留；CROSS JOIN 是笛卡兒積，N 列配 M 列得 N×M 列。

05 — JOIN

JOIN 的第一個陷阱

同一個條件，放在 ON 和放在 WHERE，結果不一樣。

放在 ON — 連接之前套用

LEFT JOIN department d
  ON e.dept_id = d.id
 AND d.name = '工程'
陳怡君 | 工程
林志明 | 工程
王美玲 | NULL
張家豪 | NULL

4 列，外連接的行為保住了

放在 WHERE — 連接之後套用

LEFT JOIN department d
  ON e.dept_id = d.id
WHERE d.name = '工程'
陳怡君 | 工程
林志明 | 工程

2 列，補上的 NULL 全被濾掉了

為什麼：ON 決定「哪些列算配對」，在連接時套用；WHERE 決定「哪些列留下」，在連接完成後套用。被 NULL 補齊的那些列，d.name 是 NULL，所以 d.name = '工程' 不成立，整列被丟掉——LEFT JOIN 就這樣退化成 INNER JOIN。

內連接時兩種寫法等價，外連接時不等價。這是 LEFT JOIN 最常見的 bug。

06 — 執行順序

寫的順序不是執行的順序

你寫的順序是 SELECT → FROM → WHERE → GROUP BY → ORDER BY。
資料庫執行的順序完全不同：

  1. FROM　把表組合成一張中間虛擬表
  2. WHERE　逐列過濾（條件為 false 或 NULL 的列被丟棄）
  3. GROUP BY　分組，計算聚合
  4. HAVING　逐組過濾
  5. SELECT　此時才計算輸出欄位
  6. ORDER BY → LIMIT

這解釋了兩件讓初學者困惑的事：

  • 為什麼過濾「組」要用 HAVING 不是 WHERE？　因為 WHERE（第 2 步）執行時，組還不存在。
  • 為什麼別名有時能用有時不能？　別名在第 5 步才產生。
PostgreSQL 的規則：輸出欄位別名可以用在 ORDER BY 與 GROUP BY，不能用在 WHERE 與 HAVING。
但 SQLite 不一樣：實測 SQLite 3.53.1 允許在 WHERE 中引用別名（WHERE annual > 600000 正常執行）。這是非 SQL 標準的擴充。
→ 這類「換個引擎就不一樣」的規則，是本主題最容易出錯的地方，第 17 頁會再談。

07 — NULL

NULL 不是值，是「不知道」

任何運算子碰到 NULL，結果既不是 true 也不是 false，而是 unknown。

SELECT 7 = NULL;     -- 結果是 NULL，不是 false
SELECT 7 <> NULL;    -- 結果也是 NULL

兩個未知值無法被認定相等，所以比較不可能產生 true。推論出一個關鍵後果：

✗ 永遠查不到東西

WHERE dept_id = NULL
（0 列）

✓ 正確寫法

WHERE dept_id IS NULL
張家豪

而且因為 WHERE 會丟棄條件為 false 或 NULL 的列，NULL 在 WHERE 中的效果等同於 false——這就是上一頁 LEFT JOIN 陷阱的底層原因。

順帶一提，計數也受影響：COUNT(*) 計算輸入列數，不管欄位值是否為 NULL；COUNT(dept_id) 只計算該欄不為 NULL 的列。
實測：SELECT COUNT(*), COUNT(dept_id) FROM employee; → 4 | 3

08 — 轉折

關鍵轉折：你沒有決定「怎麼做」

到這裡為止，我們學的都是「怎麼說出想要什麼」。
但 SQL 是宣告式（declarative）語言——你只說要什麼，不說怎麼拿。

同一個 SQL 陳述式，可能有數十、數百甚至數千種實作方式，取決於查詢的複雜度與資料庫結構。

查詢最佳化器（query optimizer）

資料庫內部的一個元件，任務是：在所有等價的執行方式中，選出磁碟 I/O 與 CPU 開銷最小的那一個。PostgreSQL 的做法是為每個查詢建出查詢計畫，選擇預估成本最低者。

所以「為什麼慢」這個問題，真正在問的是：
最佳化器為什麼選了那條慢的路？

從演算法的角度看，最佳化器是在「等價查詢計畫」構成的空間裡做搜尋，目標函數是預估成本。接下來三頁，我們看它在搜尋什麼。

09 — 成本

慢在哪裡：全表掃描的成本

沒有索引時，資料庫必須從第一列開始讀完整張表。成本隨表的大小成長。

資料不是一列一列從磁碟拿的，而是以頁（page）為單位。PostgreSQL 的頁通常是 8 kB，表與索引都存成固定大小的頁陣列。

PostgreSQL 的一頁（8 kB） ┌──────────────────────────────┐ │ PageHeaderData 24 bytes │ ├──────────────────────────────┤ │ 行指標 →→→ │ 每筆 4 bytes，(偏移量, 長度) ├──────────────────────────────┤ │ │ │ 剩餘空間 │ │ │ ├──────────────────────────────┤ │ ←←← 列資料 │ 一個 item 就是一列 └──────────────────────────────┘

所以成本模型也以頁計價。PostgreSQL 預設 seq_page_cost = 1.0，代表一次循序頁讀取。官方範例：

表 tenk1：345 頁、10,000 列
全表掃描成本 = (345 × seq_page_cost 1.0) + (10000 × cpu_tuple_cost 0.01) = 445
→ 成本 = 讀頁成本 + 每列的 CPU 成本，而讀頁是主要項。想變快，就要少讀頁。

10 — 索引

索引怎麼救：B-tree

索引就是一個資料結構。PostgreSQL 與 MySQL 的預設索引型別都是 B-tree。

┌─────── 根節點 ───────┐ │ 指向下層，記錄最大鍵值 │ └──┬───────────┬───────┘ ▼ ▼ ┌────────┐ ┌────────┐ 分支節點（路標） └──┬──┬──┘ └──┬──┬──┘ ▼ ▼ ▼ ▼ 葉節點 [..]↔[..]↔[..]↔[..]↔[..] 雙向鏈結串列，維持邏輯順序

為什麼樹很淺

每個節點容納數百筆項目。樹深隨項目數呈對數成長，每多一層容量就乘上分支因子。

實務上數百萬筆的索引，樹深通常只有四到五層。

為什麼查找快

從根節點往下，每層掃描節點內項目找到第一個 ≥ 搜尋鍵的值，沿參照下行，直到葉節點。

因為樹是平衡的，每次查找步數相同，等於樹深。

實測（SQLite，employee 的 dept_id 上建索引）：

EXPLAIN QUERY PLAN SELECT name FROM employee WHERE dept_id = 1;
→ SEARCH employee USING INDEX idx_emp_dept (dept_id=?)

SEARCH 而非 SCAN——資料庫不再讀完整張表了。

11 — 索引失效

索引救不了的時候

索引存的是原始值、按序排列。只要查詢條件破壞了「有序前綴」這件事，索引就用不上。以下全部於 SQLite 實測：

查詢條件執行計畫結果
name LIKE '%君'SCAN employee✗ 全表掃描
UPPER(name) = '陳怡君'SCAN employee✗ 全表掃描
name >= '陳' AND name < '陳倀'SEARCH … USING INDEX idx_emp_name✓ 走索引

後綴通配失效，是因為索引按開頭排序——「以某字結尾」的資料散落在整棵樹中。
函數包住欄位失效，是因為索引存的是 name 的值，不是 UPPER(name) 的值。補救方式是建函數式索引（PostgreSQL 7.4 起）或生成欄位上的索引（MySQL 5.7 起）。

但「前綴通配就一定能用索引」是錯的。SQLite 的 LIKE 最佳化有六項條件，必須全部滿足。實測同一句 name LIKE '陳%'：
欄位設定執行計畫
預設 BINARY collationSCAN employee　✗
COLLATE NOCASESEARCH … USING INDEX　✓
PRAGMA case_sensitive_like=ONSEARCH … USING INDEX　✓
而手寫的等價範圍條件在三種設定下都走索引。所以不是索引不能用，是最佳化的前提條件沒成立。

12 — 複合索引

多欄索引：順序決定一切

複合索引是跨多欄建的單一 B-tree。項目先依第一欄排序，第二欄只在第一欄相同的列之間決定順序。

像一本先依姓、再依名排序的電話簿。只知道姓，可以查；只知道名，幾乎無法查——因為同名的人散落在整本書裡。

實測（索引建在 employee(dept_id, salary)）：

✓ 約束了前導欄位

WHERE dept_id = 1
  AND salary > 50000
SEARCH employee USING INDEX
idx_emp_dept_salary
(dept_id=? AND salary>?)

✗ 只約束非前導欄位

WHERE salary > 50000
SCAN employee

索引完全用不上

最左前綴規則：第一欄永遠可用於搜尋；其他欄位只有在它前面的欄位也被約束時才可用。

MySQL 說法：最佳化器可使用複合索引的任何最左前綴。索引 (a, b, c) 支援 (a)、(a, b)、(a, b, c) 三種查找。
PostgreSQL 的建議較保守：複合索引應節制使用，超過三欄的索引除非表的使用方式極為固定，否則不太可能有幫助。

額外好處：覆蓋索引。如果查詢需要的欄位全部都在索引裡，資料庫連表都不用回去讀。SQLite 實測同一個索引 (dept_id, salary)：
查詢執行計畫
SELECT dept_id, salary …SEARCH … USING COVERING INDEX　✓ 不回表
SELECT dept_id, name …SEARCH … USING INDEX　需回表取 name
這也是 SELECT * 幾乎必然要回表的原因。PostgreSQL 稱之為 index-only scan，並可用 INCLUDE 把額外欄位塞進索引；但它還需要可見性映射配合，不是一定省得到。

13 — 代價

索引不是免費的

看到這裡很容易得出「那就每欄都建索引」的結論。那是錯的。

浪費空間

每個索引都佔儲存空間，即使從來沒有查詢用到它。

浪費最佳化器時間

資料庫必須評估所有可用索引才能決定用哪一個，多餘的索引增加規劃開銷。

拖慢所有寫入

insert、update、delete 都必須同時更新該表上的每一個索引。資料庫在每次寫入時自動維護 B-tree，這就是代價來源。

所以目標不是「索引越多越好」，而是最佳的索引集合：足以讓重要查詢變快，而不必為效益低又拖慢寫入的索引付出代價。

誠實的但書：MySQL 官方文件沒有量化這些成本，也沒有給出選擇索引的規則。任何「索引會讓寫入慢 N 倍」的說法都不是來自官方文件。

14 — 最佳化器

資料庫怎麼決定

最佳化器要做兩個決定：用什麼方式存取每張表，以及用什麼演算法接起來。

PostgreSQL 的三種連接策略：

策略怎麼運作官方說明的優勢
Nested loop對左側的每一列，把右側掃一次容易實作但可能非常慢；右側能用索引掃描時是好選擇
Merge join兩邊依連接屬性排序，再平行掃描合併每個關聯只掃一次
Hash join右側載入雜湊表，左側逐列探測文件未給出偏好指引

而選哪一種，依據的是統計估計，不是真實資料：

  • PostgreSQL 的列數估計來自 ANALYZE 的隨機取樣，會在不同次執行間變動。
  • SQLite 沒有統計時用猜測值（例如假設每個最左索引值平均有 10 筆重複）。
  • MySQL 的 rows 對 InnoDB 而言是估計值。
這解釋了「昨天很快今天很慢」：統計過時 → 估計失準 → 選錯計畫。PostgreSQL 文件也警告成本不隨表大小線性變化，玩具表上的結果不可外推到正式環境。

15 — 動手

自己看出來

不用猜。每個資料庫都有指令可以直接問它「你打算怎麼執行」。

-- SQLite
EXPLAIN QUERY PLAN SELECT name FROM employee WHERE salary = 62000;
→ SCAN employee

SCAN 就是答案：salary 上沒有索引，所以要讀完整張表。建了索引之後同一句會變成 SEARCH … USING INDEX …。

你只需要認得兩個字：

SCAN

全表掃描。資料量大時就是你要找的問題。

SEARCH … USING INDEX

走索引。後面括號會告訴你用了哪些欄位。

其他引擎的指令不同（第 17 頁詳述）：PostgreSQL 用 EXPLAIN（加 ANALYZE 會實際執行並顯示真實列數與毫秒數）；MySQL 用 EXPLAIN，看 type 欄位是不是 ALL、key 是不是 NULL。

PostgreSQL 判讀重點：預估列數與實際列數是否接近。差很多就代表統計過時。文件也說明完全吻合在實務上是不尋常的。

16 — 但書

一個重要但書：三家引擎不一樣

前面每一條規則，都有它適用的引擎與版本。把某一家的行為當成「資料庫都這樣」，是這個主題最常見的錯誤。

PostgreSQL 18MySQL 8.0SQLite
執行計畫指令EXPLAIN / EXPLAIN ANALYZEEXPLAINEXPLAIN QUERY PLAN
輸出形式計畫節點樹表格，一列一張表高階概觀
沒用索引的訊號Seq Scantype: ALL、key: NULLSCAN
連接演算法nested loop / merge / hashBNL / BKA / hash join只有 nested loop
WHERE 能用別名？不能（文件明言）—可以（非標準擴充）
本簡報的誠實聲明：所有標示「✓ 已實跑」的驗證都是在 SQLite 3.53.1 上執行的。這些結果只能證明 SQLite 的行為，不能當作 PostgreSQL 或 MySQL 的證據。凡是 PostgreSQL / MySQL 的陳述，依據的是其官方文件，不是實測。

製作過程中，忠實度檢查抓到的兩個錯誤——「別名不能用在 WHERE」和「LIKE 前綴一定走索引」——都是把單一引擎的行為當成通用規則。這一頁就是為此而存在。

17 — 收束

回到第一頁的問題

SELECT name FROM employee WHERE dept_id = 1;

現在這句話可以完整回答了：

  1. 你寫的是宣告式的 SQL，只說要什麼。
  2. 最佳化器在所有等價執行方式中，依統計估計挑成本最低的。
  3. 沒有索引，它只能全表掃描，一頁一頁讀。
  4. 有合適的索引，它能走 B-tree，數百萬筆資料只需走訪四到五層。
  5. 但索引有失效條件（前綴通配、函數包裹、非前導欄位、collation 不符）也有代價（空間、寫入）。
  6. 要知道它到底選了哪條路，就問它：SQLite 用 EXPLAIN QUERY PLAN，PostgreSQL 與 MySQL 用 EXPLAIN——不要猜。
一句話帶走：SQL 讓你不必管「怎麼做」，但當它變慢時，你必須知道資料庫在你背後做了什麼選擇——以及你的寫法如何限制了它的選項。
