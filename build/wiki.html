A1 — 關聯式模型：表、列、欄、鍵3 處引註

來源：S6 適用範圍：通用

內容

  • 關聯式資料庫把資料存成表（table）。表由欄（column）定義結構，資料以列（row）為單位逐筆存放。S6
  • 一個查詢的起點是 FROM，它把一或多張表組合成一張中間虛擬表（intermediate virtual table），後續所有子句都在這張虛擬表上運作。S6
  • 表與表之間透過欄位值互相參照。例如 t1.num 對應 t2.num，JOIN 就是依這種對應關係把兩張表拼起來。S6

教學用例（來自 S6 官方範例）

t1:  num | name        t2:  num | value
      1  | a                 1  | xxx
      2  | b                 3  | yyy
      3  | c                 5  | zzz

此範例貫穿 A4（JOIN 種類），兩者使用同一組資料。

A2 — 宣告式語言與查詢最佳化5 處引註

來源：S11, S2 適用範圍：通用

內容

  • SQL 最重要的特性是它是宣告式（declarative）語言而非程序式語言：使用者描述要什麼結果，不描述如何取得。S11
  • 因此，同一個 SQL 陳述式可能有數十、數百甚至數千種實作方式，取決於查詢複雜度與資料庫結構。S11
  • 從中挑一個的元件叫查詢規劃器 / 最佳化器（query planner / optimizer）。它的任務是選出能以最少磁碟 I/O 與 CPU 開銷完成查詢的演算法。S11
  • PostgreSQL 的做法是對每個查詢建出查詢計畫，並選擇預估成本最低的那一個。S2
  • SQLite 採成本基礎（cost-based）：估算各競爭計畫的 CPU 與磁碟 I/O 成本，選預期最快者。S11

教學重點

「你寫的 SQL 決定要什麼，不決定多快」——整個效能主題的出發點。 從演算法角度看，最佳化器是在等價查詢計畫的空間中做搜尋，目標函數是預估成本。

A3 — 查詢的邏輯執行順序5 處引註

來源：S7, S6 適用範圍：PostgreSQL 18 文件明列；概念為 SQL 標準通用

內容

PostgreSQL SELECT 文件明列的邏輯求值順序（步驟 1–10）：S7

  1. WITH 子查詢先計算，作為暫時表供 FROM 參照
  2. FROM 清單計算，多個項目互相 cross join
  3. WHERE 移除不符合條件的列
  4. 若有 GROUP BY 或聚合函數，進行分組並計算聚合；接著 HAVING 移除不符合的組
  5. 由 SELECT 輸出運算式計算出輸出列
  6. DISTINCT / DISTINCT ON 移除重複列（預設 ALL 保留）
  7. UNION / INTERSECT / EXCEPT 合併多個 SELECT 的結果
  8. ORDER BY 排序
  9. LIMIT（或 FETCH FIRST）與 OFFSET 取子集
  10. 鎖定子句（FOR UPDATE 等）鎖住選出的列

Table Expressions 文件將前半段描述為一條管線：FROM 建虛擬表 → WHERE 逐列過濾（條件為 false 或 NULL 的列被丟棄，發生在分組之前）→ GROUP BY 分組並計算聚合 → HAVING 過濾組。S6

別名可用範圍（經原始文件修正過的重點）

  • 輸出欄位別名可以用在 ORDER BY 與 GROUP BY。GROUP BY 可用名稱或序號參照輸出欄位；名稱有歧義時，GROUP BY 視之為輸入欄位。S7
  • 輸出欄位別名不能用在 WHERE 與 HAVING，必須完整寫出運算式。S7
  • 文件未明述理由，但由步驟順序可推：WHERE（步驟 3）與 HAVING（步驟 4）都早於輸出運算式的計算（步驟 5）。S7

⚠ 寫稿注意：不可寫成「別名不能用在 WHERE 和 GROUP BY」。GROUP BY 是可以的。

A4 — JOIN 的種類與語意10 處引註

來源：S6 適用範圍：PostgreSQL 18 文件；語意為 SQL 標準通用

內容（沿用 A1 的 t1 / t2 範例）

  • CROSS JOIN：笛卡兒積，T1 的每一列與 T2 的每一列配對，N 與 M 列產生 N × M 列。等同於 INNER JOIN ... ON TRUE，也等同於用逗號分隔的 FROM 清單。S6
  • INNER JOIN（未加修飾詞時的預設）：對每一對滿足連接條件的 (T1列, T2列) 輸出一列。兩邊未配對到的列都被丟棄。S6
  • SELECT * FROM t1 INNER JOIN t2 ON t1.num = t2.num; → 1 a 1 xxx / 3 c 3 yyy
  • LEFT OUTER JOIN：先做 inner join，再為每一個在 T2 中無配對的 T1 列補上一列，T2 側所有欄位填 NULL。每一列 T1 至少出現一次。S6
  • 比 inner join 多出：2 b | NULL | NULL
  • RIGHT OUTER JOIN：反向，為每一個未配對的 T2 列補列，T1 側填 NULL。每一列 T2 至少出現一次。S6
  • 多出：NULL | NULL | 5 | zzz
  • FULL OUTER JOIN：先做 inner join，再把兩邊未配對的列都補上（各自以 NULL 填滿對側）。S6
  • OUTER 一律可省略；LEFT、RIGHT、FULL 本身就蘊含外連接。S6

ON 與 WHERE 的關鍵差異（外連接才看得出來）

ON 接受任何布林運算式，在連接之前套用，影響哪些列算配對；WHERE 在連接之後套用，影響哪些列留下。S6

SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num AND t2.value = 'xxx';
-- 3 列：1 a 1 xxx / 2 b NULL NULL / 3 c NULL NULL

SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num WHERE t2.value = 'xxx';
-- 1 列：1 a 1 xxx

內連接時兩種寫法結果相同；外連接時不同。S6 這是「LEFT JOIN 後面接 WHERE 會把外連接打回內連接」的官方依據。

ON / USING / NATURAL

  • USING (a, b) 等價於 ON T1.a = T2.a AND T1.b = T2.b，且輸出會把配對欄位合併成一份。用 ON 時配對欄位會出現兩次。S6
  • NATURAL 等同於對所有同名欄位做 USING。文件明言 NATURAL 比 USING 風險高得多，因為新增一個同名欄位的綱要變更會無聲地改變連接行為。若兩表無同名欄位，NATURAL 的行為等同 CROSS JOIN。S6

A5 — NULL 與三值邏輯9 處引註

來源：S5, S6 適用範圍：PostgreSQL 18 文件；SQL 標準行為

內容

  • 一般比較運算子（=、<>、< 等）在任一邊為 null 時回傳 null（意為 unknown），而非 true 或 false。S5
  • SELECT 7 = NULL; → null
  • SELECT 7 <> NULL; → null
  • 原因：NULL 代表未知值，兩個未知值無法被認定相等，所以比較不可能產生 true。S5
  • 因此 expression = NULL 永遠不會配對到任何列。正確寫法是 IS NULL / IS NOT NULL。S5
  • PostgreSQL 提供 transform_null_equals 設定，啟用後會把 x = NULL 改寫為 x IS NULL，但文件建議修正應用程式以符合 SQL 標準，而非依賴此設定。S5

IS DISTINCT FROM

  • IS DISTINCT FROM：把 null 當成可比較的值。兩邊非 null 時行為同 <>；兩邊都是 null 回傳 false；恰好一邊是 null 回傳 true。S5
  • IS NOT DISTINCT FROM：兩邊非 null 時行為同 =；兩邊都 null 回傳 true；恰好一邊 null 回傳 false。S5
  • 文件說明這組述詞實際上是把 null 當作普通值而非「未知」來處理。S5
運算式 結果
1 IS DISTINCT FROM NULL true
NULL IS DISTINCT FROM NULL false
1 IS NOT DISTINCT FROM NULL false
NULL IS NOT DISTINCT FROM NULL true

布林測試

IS TRUE / IS NOT TRUE / IS FALSE / IS NOT FALSE / IS UNKNOWN / IS NOT UNKNOWN 一律回傳 true 或 false，永不回傳 null，即使運算元為 null。S5

運算式 結果
NULL::boolean IS TRUE false
NULL::boolean IS NOT TRUE true
NULL::boolean IS UNKNOWN true

與 A3 的交互作用

WHERE 會丟棄條件為 false 或 NULL 的列（見 A3 / S6）。這代表 NULL 在 WHERE 中的效果等同於 false——這是 NULL 最常造成意外的地方。

A6 — 聚合與分組15 處引註

來源：S6, S7, S15 適用範圍：PostgreSQL 18 文件

分組與過濾

  • GROUP BY 把通過 WHERE 的列分組，聚合函數在每一組上計算。S6
  • HAVING 過濾組，一如 WHERE 過濾列。HAVING 可以參照分組運算式與聚合結果。S6
  • 含聚合呼叫、或有 HAVING 而無 GROUP BY 的查詢，整個被視為一組，回傳一列（若被 HAVING 濾掉則零列）。S6
  • 視窗函數在分組、聚合與 HAVING 之後求值。S6

count(*) 與 count(expression) 的差異

  • count(*) 計算輸入列數，不論任何欄位值是否為 null。S15
  • count(expression) 只計算該引數不為 null 的輸入列。S15
  • 兩者都回傳 bigint。S15
  • 文件另註：對整張表做 count(*) 是昂貴的，PostgreSQL 必須掃描整張表，或掃描一個涵蓋其所有列的索引。S15

聚合函數如何處理 NULL

  • 多數通用聚合函數忽略 null，其說明都寫明對「非 null 的輸入值」運算。這涵蓋 any_value、avg、bit_and、bit_or、bit_xor、bool_and、bool_or、every、max、min、range_agg、string_agg、sum、xmlagg。S15
  • 部分聚合函數包含 null：array_agg（非陣列輸入時）會收集 null，json_agg 也包含；json_agg_strict 與 jsonb_agg_strict 則跳過。S15
  • 假設集聚合（rank、dense_rank、percent_rank、cume_dist）明確不是 strict 的，不會丟棄含 null 的列。S15
  • 統計類聚合使用 N = 所有輸入運算式皆非 null 的列數；計算無意義時（例如 N 為 0）回傳 null。S15

沒有任何列時回傳什麼

  • 除了 count 以外，這些函數在沒有選出任何列時回傳 null。S15
  • 文件特別指出 array_agg 回傳 null 而非空陣列。需要以 0 或空陣列代替時應使用 coalesce。S15
  • sum、avg、max、min 在無輸入列時皆回傳 null。S15

⚠ 寫稿注意：文件未明述「所有輸入皆為 null」時的結果。由「忽略 null」可推論應為 null，但這是推論而非文件陳述，簡報中不可寫成文件的說法。

B1 — 表的實體儲存與掃描成本10 處引註

來源：S2, S8, S17 適用範圍：PostgreSQL 18（頁面結構與成本模型）、MySQL 8.0（無索引行為）

頁（page）是什麼

  • PostgreSQL 的表與索引都存成固定大小的頁陣列，一頁通常 8 kB。伺服器可編譯成不同頁大小，但一個安裝只支援一種。S17
  • 一頁由五個部分組成，從頁首依序為：S17 1. PageHeaderData：24 位元組的一般資訊，含剩餘空間指標 2. ItemIdData（line pointer，行指標）：每筆 4 位元組，存放指向某個項目的 (偏移量, 長度) 對 3. 剩餘空間：行指標從前方長入，項目從後方長入 4. Items（項目）：在表中，每個項目就是一列；項目從未配置空間的尾端往前配置 5. Special space：存取方法專屬資料，一般表為空
  • 行指標一旦配置就不會移動，即使項目本身為了壓實空間而被搬動。因此它的索引可作為長期參照。ItemPointer（CTID）就是「頁碼 + 行指標索引」。S17

列（heap tuple）的結構

每一列的結構相同：S17 - 固定大小標頭，多數機器上為 23 位元組 - 選用的 null bitmap，只在 t_infomask 設有 HEAP_HASNULL 時存在，每欄一個位元（1 為非 null，0 為 null）；不存在時所有欄位視為非 null - 使用者資料，起始於 t_hoff 指定的偏移量

⚠ 文件未說明一列是否可以跨頁，只說表中所有頁在邏輯上等價，任何列可存於任何頁。S17 變動長度的值可能內嵌存放或存入 TOAST 表，也可能被壓縮；文件未在此頁描述門檻與機制。S17

掃描成本模型

  • 沒有索引時，MySQL 必須從第一列開始讀完整張表；成本隨表的大小成長。有索引時可直接定位到資料檔中的相關位置。S8
  • PostgreSQL 的成本模型以頁為單位計價。預設 seq_page_cost = 1.0，代表一次循序磁碟頁讀取；其他成本參數相對於它設定。S2
  • 官方範例：表 tenk1 有 345 頁、10,000 列，全表掃描預估成本為 (345 × seq_page_cost 1.0) + (10000 × cpu_tuple_cost 0.01) = 445。S2 → 成本 = 讀頁成本 + 每列的 CPU 成本，且讀頁是主要項。

索引不是永遠有利

MySQL 文件指出索引在以下情況較無用：表很小、或查詢需處理大表中絕大部分的列。此時循序讀取比索引走訪更快，且能把磁碟尋道次數降到最低，即使不是每一列都需要。S8

B2 — B-tree 索引原理12 處引註

來源：S12, S1, S8 適用範圍：通用（PostgreSQL 18 / MySQL 8.0 皆以 B-tree 為預設）

為什麼需要樹

  • 索引的葉節點（leaf node）在磁碟上並非按鍵值順序存放，所以光有葉節點無法快速定位。S12
  • 葉節點之間以雙向鏈結串列（doubly linked list）相連，記錄其邏輯順序。S12
  • 葉節點之上是分支節點（branch node）作為路標：每一筆分支項目記錄它所指向之葉節點中的最大鍵值。分支層層疊起，直到最上層只剩單一根節點（root node）。S12

為什麼樹很淺

  • 每個節點容納大量項目，通常數百筆。樹深隨項目數呈對數成長，每增加一層，容量就乘上節點的分支因子（fan-out）。S12
  • 文章以每節點 4 筆為例：深度 3 容納 64 筆，每多一層就是四倍；深度 5 約 1,024 筆，深度 10 約一百萬筆。S12
  • 若每節點數百筆，每多一層約可支撐一百倍的資料量。實務上數百萬筆的索引，樹深通常只有四到五層。S12

走訪成本

  • 查找從根節點開始，依遞增順序掃描節點內的項目，找到第一個大於或等於搜尋鍵的值，沿該參照往下，重複直到葉節點。S12
  • 因為樹是平衡的，每次查找的步數都相同，等於樹深。S12
  • 樹深是項目數的對數（底數為每節點項目數），所以資料增加時查找成本成長得非常慢。S12

各引擎的預設

  • PostgreSQL 提供 B-tree、Hash、GiST、SP-GiST、GIN、BRIN，外加 bloom 擴充。B-tree 是預設，CREATE INDEX 不指定 USING 時建的就是 B-tree。S1
  • MySQL 的多數索引（PRIMARY KEY、UNIQUE、INDEX、FULLTEXT）以 B-tree 儲存。例外：空間資料型別用 R-tree，MEMORY 表另支援 hash 索引，InnoDB 的 FULLTEXT 用倒排串列。S8

代價

資料庫在每次 insert、update、delete 時都自動維護這棵樹，這為寫入操作增加額外負擔。S12（詳見 B6）

B3 — 複合索引與最左前綴12 處引註

來源：S13, S8, S3, S11 適用範圍：各引擎規則一致性高，但細節有差（見 D1）

排序方式

  • 複合（concatenated）索引是跨多欄建的單一 B-tree。其項目先依第一欄排序；第二欄只在第一欄相同的列之間決定順序，後續欄位依此類推。S13
  • 因此欄位順序決定了哪些查詢能用這個索引。S13

最左前綴規則

  • 第一欄永遠可用於搜尋。其他欄位只有在它前面的欄位也被約束時才可用。S13
  • MySQL：最佳化器可使用複合索引的任何最左前綴。索引 (col1, col2, col3) 支援 (col1)、(col1, col2)、(col1, col2, col3) 三種查找。S8
  • PostgreSQL：B-tree 索引可搭配其任何欄位子集的條件使用，但在前導（最左）欄位被約束時最有效率。前導欄位上的等值約束，加上第一個沒有等值約束之欄位上的不等式約束，會被用來限制索引的掃描範圍；再右邊欄位的約束只在索引內檢查，能省去訪表，但不必然縮小必須掃描的索引範圍。S3

哪些查詢用不到

  • 只過濾非前導欄位的查詢：符合的列散落在整棵樹中，資料庫通常退回全表掃描。文章的例子是主鍵 (employee_id, subsidiary_id) 卻只用 subsidiary_id 查詢。S13
  • 類比：像一本先依姓、再依名排序的電話簿。只知道姓可以查，只知道名就幾乎無法查。S13
  • 把常被過濾的欄位放在前面（改成 (subsidiary_id, employee_id)），所有符合的列就會相鄰，資料庫可做索引範圍掃描（index range scan）。S13

SQLite 的精確規則

索引 (a,b,c,...,z)：S11 - 前導欄位必須以 =、IN 或 IS 約束。 - 最右側被使用的欄位可用不等式，最多兩個（夾出允許範圍）。 - 不允許有缺口。若 c 未被約束，d–z 上的條件都不能使用。 - 不等式約束之欄位右側的欄位通常不可用（skip-scan 為例外）。

官方範例（索引 (a,b,c,d)）： | WHERE 條件 | 可用欄位 | |---|---| | a=5 AND b IN (1,2,3) AND c IS NULL AND d='hello' | a, b, c, d 全部 | | a=5 AND b IN (1,2,3) AND c>12 AND d='hello' | 只有 a, b, c（d 在不等式右側）| | a=5 AND b IN (1,2,3) AND d='hello' | 只有 a, b（c 是缺口）| | b IN (1,2,3) AND c NOT NULL AND d='hello' | 索引不可用（a 未約束）→ 全表掃描 |

設計建議

  • 一個排序良好的複合索引通常優於兩個獨立索引，可節省儲存並減少寫入負擔。S13
  • PostgreSQL 文件則偏保守：複合索引應節制使用；多數情況單欄索引就夠且更省空間與時間；超過三欄的索引除非表的使用方式極為固定，否則不太可能有幫助。S3
  • PostgreSQL 的複合索引最多 32 欄（含 INCLUDE 欄位）。S3

B4 — 索引失效的典型情境11 處引註

來源：S1, S14, S11, S8 適用範圍：各引擎皆有，但條件細節不同（見 D1）

1. 前綴通配：LIKE '%bar'

PostgreSQL 18：B-tree 索引只有在模式是常數且錨定於字串開頭時才可用於 LIKE 與 ~。S1 - 可用：col LIKE 'foo%'、col ~ '^foo' - 不可用：col LIKE '%bar' - 地區設定但書：若資料庫未使用 C locale，索引必須以特殊的 operator class 建立才能支援模式比對查詢。S1 - ILIKE 與 ~* 只有在模式以非字母字元（不受大小寫轉換影響的字元）開頭時才能用索引。S1

SQLite 的條件更細（LIKE/GLOB optimization 必須全部滿足）：S11 1. 右側是字串常值（或綁定到字串常值的參數），且不以通配字元開頭 2. 數值型的左運算元不得使 運算子為真。或者 (a) 左運算元是具 TEXT affinity 的索引欄位，或 (b) 模式不以 - 或數字開頭 - 文件給的理由：9<10 但 '9'>'10'——數字不按字典序排列 3. 內建 LIKE/GLOB 函數未被 sqlite3_create_function() 覆寫 4. GLOB：欄位須使用內建 BINARY collation 5. LIKE：case_sensitive_like 為 ON 時欄位須用 BINARY，為 OFF（預設）時須用 NOCASE。只有這兩種組合可最佳化 6. 若用 ESCAPE，跳脫字元須為 ASCII 或單位元組 UTF-8

機制：對非通配前綴 x，令 y 為同長度中最小的、比較大於 x 的字串（例：'hello' → 'hellp'），SQLite 加入兩個虛擬條件 column >= x AND column < y。原本的 LIKE 通常仍逐列檢查；只有在模式恰為 column LIKE x%（單一尾端通配）時才會省略。S11

2. 函數包裹欄位：WHERE UPPER(col) = ...

  • 對索引欄位套用函數會使資料庫無法使用該欄位上的普通索引。S14
  • 例：LAST_NAME 上的索引，只在搜尋時大小寫與儲存值一致才有用；為了大小寫不敏感而用 UPPER / LOWER 包住欄位，就是問題所在。S14
  • 補救方式：S14
  • 函數式 / 運算式索引：PostgreSQL（7.4 起）、Oracle（8i 起）、Db2 LUW（10.5 起，不允許使用者自訂函數）
  • 計算欄位 / 生成欄位：SQL Server 2000 起支援索引化計算欄位；MySQL 5.7 起支援生成欄位上的索引
  • 以上皆不可得時：新增一個實體欄位存放函數結果，用觸發器或應用程式維護，對它建索引，並把 WHERE 改寫成針對該欄位、不含運算式

⚠ 寫稿注意：S14 的頁面未說明資料庫在索引失效後改用什麼計畫（是否為全表掃描），也未提供日期函數的例子。不可憑推測補上。

3. 型別不一致

MySQL：連接欄位的型別與大小相同時索引效率最好；比較不同型別（例如字串欄位對數值）可能導致索引無法使用。S8

4. 前導欄位未約束

見 B3。SQLite 範例 WHERE b IN (1,2,3) AND c NOT NULL AND d='hello'（索引 (a,b,c,d)）→ a 未約束，索引不可用，全表掃描。S11

5. SQLite 的 unary +

+x=5 中的一元 + 會使該條件無法約束索引。文件警告這是最後手段的繞道方式，且會移除 affinity，可能改變比較語意。S11

B5 — 覆蓋索引與 index-only scan13 處引註

來源：S4, S8, S10 適用範圍：PostgreSQL 18 機制說明；MySQL 8.0 對應概念

定義

index-only scan 只用索引項目回答查詢，不回表（heap）取對應的資料列。一般索引掃描必須同時讀索引與 heap，而 heap 的讀取往往是分散的，所以省掉它能大幅節省 I/O。S4

必要條件

  1. 索引型別須支援。B-tree 永遠支援；GiST 與 SP-GiST 僅部分 operator class 支援；其他型別（含 GIN）不支援。索引必須儲存或能重建每筆項目的原始值——GIN 項目通常只存部分值，故不合格。S4
  2. 查詢只能參照索引中儲存的欄位。以表上有 x, y, z、索引建在 (x, y) 為例：S4 sql SELECT x, y FROM tab WHERE x = 'key'; -- 可用 SELECT x FROM tab WHERE x = 'key' AND y < 42; -- 可用 SELECT x, z FROM tab WHERE x = 'key'; -- 不可用 SELECT x FROM tab WHERE x = 'key' AND z < 42; -- 不可用

為什麼還是常常要回表（PostgreSQL 特有）

  • MVCC 下的列可見性只記錄在 heap tuple 中，不在索引項目裡。S4
  • 每個表頁在可見性映射（visibility map）中有一個位元，當該頁上所有列對所有現在與未來的交易都可見時被設定。掃描時對每筆候選索引項目檢查對應 heap 頁的該位元：S4
  • 位元已設：該列確定可見，直接回傳索引中的值
  • 位元未設：必須讀 heap tuple 檢查可見性，相對一般索引掃描沒有節省
  • 可見性映射比它所描述的 heap 小約四個數量級，通常快取在記憶體中。因此 index-only scan 只有在表中相當大比例的頁都是 all-visible 時才划算——這對大致靜態的資料很常見。S4

INCLUDE 覆蓋索引

CREATE INDEX tab_x_y ON tab (x) INCLUDE (y);
  • y 存在索引中但不屬於搜尋鍵，不被索引機制解讀，因此不需要是索引能處理的型別。S4
  • 唯一性只約束鍵欄位：CREATE UNIQUE INDEX tab_x_y ON tab (x) INCLUDE (y); 僅對 x 唯一。S4
  • 代價：payload 欄位重複表中資料、使索引變大，可能拖慢搜尋；過寬的欄位可能使 tuple 超過索引最大尺寸導致 insert 失敗。只有在表變動夠慢、index-only scan 真能避開回表時才有幫助。S4
  • 限制：運算式不能作為 included 欄位；只有 B-tree、GiST、SP-GiST 支援 INCLUDE。S4
  • INCLUDE 出現之前的做法是把 y 當成尾端鍵欄位 CREATE INDEX tab_x_y ON tab (x, y);。查找可行，但無法只對 x 強制唯一。非鍵欄位也不會進入 B-tree 上層，使上層 tuple 保持精簡。S4

MySQL 的對應說法

查詢只需要索引中包含的欄位時，值直接從索引樹讀出，不查資料列——這就是覆蓋索引。S8 在 EXPLAIN 的 Extra 欄位顯示為 Using index。S10

B6 — 索引的代價5 處引註

來源：S9, S12, S4 適用範圍：通用

三項成本

MySQL 文件列出三點：S9 - 浪費空間：每個索引都佔儲存空間，即使沒有任何查詢用到它。 - 浪費最佳化器時間：MySQL 必須評估可用的索引來決定用哪一個，多餘的索引增加規劃開銷。 - 拖慢寫入：insert、update、delete 都必須同時更新受影響表上的每一個索引。

Use The Index, Luke 的對應說法：資料庫在每次 insert、update、delete 時自動維護 B-tree，這為寫入操作增加負擔。S12

結論

  • 必須在這些成本與查詢速度之間取得平衡。在 WHERE 子句用到的欄位上建索引能加快 SELECT，但為每一個可能的欄位都建索引會適得其反。目標是最佳的索引集合：足以讓重要查詢變快，而不必為效益低又拖慢寫入的索引付出代價。S9
  • MySQL 文件未量化這些成本，也未給出選擇索引的規則。S9
  • 覆蓋索引的 payload 欄位會重複表中資料、使索引變大，可能拖慢搜尋。S4

⚠ 寫稿注意：不可寫出「索引會讓寫入慢 N 倍」這類具體數字，來源未提供任何量化。

C1 — 執行計畫與最佳化器10 處引註

來源：S2, S11 適用範圍：PostgreSQL 18、SQLite

最佳化器在做什麼

  • PostgreSQL 為收到的每個查詢設計一個查詢計畫（query plan），並選擇預估成本最低者。EXPLAIN 顯示該計畫而不執行查詢。S2
  • SQLite：給定單一 SQL 陳述式，可能有數十、數百甚至數千種實作方式。規劃器的任務是選出磁碟 I/O 與 CPU 開銷最小的那一個。它是成本基礎的，估算各競爭計畫的成本並選預期最快者。S11
  • 當有多個索引是候選時，SQLite「估算使用每個選項完成查詢所需的總工作量」，選工作量估計最小者。S11

計畫的結構

計畫是一棵計畫節點（plan node）樹：S2 - 掃描節點（scan node）位於底部，從表（或 VALUES、FROM 中的集合回傳函數等非表來源）回傳原始列。 - 上層節點對這些列執行連接、聚合、排序等工作。 - 輸出每個節點一行，以縮排表示樹狀結構。 - 第一行（最上層節點）給出整個計畫的預估總成本，這就是規劃器試圖最小化的數字。

成本數字怎麼讀

每個節點行的形式為 (cost=startup..total rows=N width=W)：S2

欄位 意義
startup cost 該節點能開始輸出之前的時間，例如 Sort 節點的排序時間
total cost 該節點執行到完成的預估成本。父節點可能提早停止讀取，例如在 LIMIT 之下
rows 該節點輸出的預估列數，不是它掃描的列數
width 預估的平均列寬，單位為位元組
  • 單位：成本是由規劃器成本參數設定的任意單位。慣例上 seq_page_cost = 1.0（一次循序磁碟頁讀取），其他參數相對於它。S2
  • 累計：上層節點的成本包含其子節點的成本。S2
  • 不計入：成本忽略傳送給用戶端與值轉文字的開銷，因為規劃器無法改變它們。S2

SQLite 的規劃細節

  • 連接順序以「多項式時間的圖演算法」決定（詳見 Next Generation Query Planner 文件），因此 50 或 60 路的連接也能在微秒內規劃完成。S11
  • ANALYZE 提供統計資訊（sqlite_stat* 表）。沒有統計時 SQLite 用猜測值，例如：最左索引值平均 10 筆重複、自動索引計價時 N = 一百萬列。文件建議用 PRAGMA optimize 保持統計最新。S11

C2 — JOIN 演算法13 處引註

來源：S16, S11, S10, S2 適用範圍：PostgreSQL 18 為主；各引擎支援度不同（見 D1）

PostgreSQL 的三種連接策略

1. Nested loop join（巢狀迴圈連接）S16 - 對左側關聯的每一列，把右側關聯掃過一次。 - 文件評價：容易實作，但可能非常慢。 - 何時是好選擇：右側關聯可用索引掃描存取時——因為目前這一列左側的值可以直接當作索引鍵。

2. Merge join（合併連接）S16 - 兩個關聯都先依連接屬性排序，然後平行掃描並合併相符的列。 - 文件評價：吸引人之處在於每個關聯只掃描一次。 - 排序可以是明確的排序步驟，也可以來自用連接鍵上的索引以正確順序掃描關聯。

3. Hash join（雜湊連接）S16 - 先掃描右側關聯，以其連接屬性為鍵載入雜湊表。 - 再掃描左側關聯，用每一列的連接值去探測（probe）雜湊表尋找相符項。

⚠ 文件未給出何時 hash join 或 merge join 優於其他策略的明確指引。唯二明述的優勢是 nested loop 的索引情境與 merge join 的單次掃描。S16

連接順序的搜尋

  • 超過兩個關聯的查詢，結果建成二元連接步驟的樹，規劃器評估不同的連接序列找出最便宜者。S16
  • 關聯數少於 geqo_threshold 時，規劃器進行近乎窮舉的搜尋。S16
  • 它偏好連接那些在 WHERE 條件中有連接子句的關聯對；沒有連接子句的配對只在某個關聯別無選擇時才考慮。S16
  • 超過 geqo_threshold 時改用啟發式方法，即基因查詢最佳化器（GEQO）。原因是窮舉在連接數多時會耗費過多時間與記憶體。S16
  • 搜尋在輕量的「路徑（path）」上進行，找到最便宜的路徑後才建出完整計畫樹交給執行器。S16

其他引擎

  • SQLite 把所有連接都實作為巢狀迴圈，沒有 hash join 或 merge join。預設最左的 FROM 表為外層迴圈，規劃器可重排迴圈以取得更好的索引；內連接可自由重排，外連接不可（不具交換律與結合律），CROSS JOIN 永不重排。S11
  • 官方範例顯示同一查詢的兩種巢狀順序在特定資料分布下差異可達約 2000 倍。S11
  • MySQL：EXPLAIN 的 Extra 顯示 Using join buffer 時，代表使用了 Block Nested Loop、Batched Key Access 或 hash join。S10
  • PostgreSQL 的判讀陷阱：merge join 在外層鍵重複時會重掃內層列，EXPLAIN ANALYZE 把這些重複計為額外的列，可能使內層子節點回報的列數膨脹。S2

教學重點

同一個 JOIN，資料庫有三種完全不同的執行方式，成本差異可以是數量級的。而選哪一種由最佳化器根據統計估計決定，不是由你寫的 SQL 決定——這回扣 A2 的宣告式特性。

C3 — 統計資訊與基數估計7 處引註

來源：S2, S11, S10 適用範圍：三引擎皆有對應機制

估計從哪來

  • PostgreSQL：列數估計來自 ANALYZE 的隨機取樣，因此會在不同次執行之間變動，也會在重新 analyze 後改變。S2
  • SQLite：ANALYZE 產生 sqlite_stat* 表。沒有統計時 SQLite 用猜測值，例如假設最左索引值平均有 10 筆重複，自動索引計價時假設 N = 一百萬列。S11
  • MySQL：EXPLAIN 的 rows 是最佳化器預期檢查的列數；對 InnoDB 而言這是估計值。filtered 是這些列中通過該表條件後剩餘的百分比估計，rows × filtered 約等於傳給連接中下一張表的列數。S10

估錯的後果與診斷

  • PostgreSQL：成本是平台相依的，且不隨表大小線性變化。玩具表上的結果不可外推到正式環境規模——規劃器在不同規模下可能選出不同的計畫。S2
  • 判讀重點是預估列數與實際列數是否接近。文件指出實務上完全吻合是不尋常的。S2
  • MySQL：檢視計畫時應確認 rows 的乘積是否與真實列數相符。若差距很大，最佳化器的統計可能已過時，執行 ANALYZE TABLE 可能有幫助。S10
  • SQLite：文件建議用 PRAGMA optimize 保持統計最新。S11

教學重點

最佳化器不是根據真實資料做決定，而是根據取樣得來的統計估計。統計過時 → 估計失準 → 選錯計畫。這是「查詢昨天很快今天很慢」的常見成因。

C4 — 怎麼讀執行計畫26 處引註

來源：S2, S10, S11 適用範圍：三引擎輸出格式完全不同（見 D2）

PostgreSQL：EXPLAIN 與 EXPLAIN ANALYZE

  • EXPLAIN 只顯示規劃器的估計值，查詢不會被執行。S2
  • EXPLAIN ANALYZE 實際執行查詢，在估計值旁加上每個節點的實際列數與執行時間，例如 (actual time=0.017..0.051 rows=10.00 loops=1)。S2
  • 實際時間單位是毫秒；成本是任意單位，兩者不可直接比較。S2
  • 節點執行多次（loops > 1）時，actual 的時間與列數是每次執行的平均值，乘上 loops 才是總量。S2
  • 因為查詢真的被執行，副作用會發生。要分析 DML 應包在 BEGIN; ... ROLLBACK; 中。S2
  • ANALYZE 會隱含啟用 BUFFERS。S2

三種掃描節點

節點 行為 何時被選中
Seq Scan 依實體順序讀過表的每一列，條件以 Filter: 套用 需要表中很大一部分時 S2
Index Scan 走訪索引，依索引順序逐筆取出對應的表列。每次取用都是隨機存取，每列成本高 回傳極少列，或 ORDER BY 與索引順序相符時 S2
Bitmap Heap Scan 兩段式，通常位於 Bitmap Index Scan 之上。後者從索引收集符合列的位置成為 bitmap，前者把這些位置排成實體順序再取列，藉此避開大部分隨機存取成本，並以 Recheck Cond: 重新檢查條件 中等選擇性：多於少數幾列但遠少於整張表時 S2

官方範例：S2

EXPLAIN SELECT * FROM tenk1 WHERE unique1 = 42;
 Index Scan using tenk1_unique1 on tenk1  (cost=0.29..8.30 rows=1 width=244)
   Index Cond: (unique1 = 42)

EXPLAIN SELECT * FROM tenk1 WHERE unique1 < 100;
 Bitmap Heap Scan on tenk1  (cost=5.06..224.98 rows=100 width=244)
   Recheck Cond: (unique1 < 100)
   ->  Bitmap Index Scan on tenk1_unique1  (cost=0.00..5.04 rows=100 width=0)
         Index Cond: (unique1 < 100)

判讀的注意事項

  • 計時儀器本身有開銷，在 gettimeofday() 較慢的系統上可能很顯著，可用 pg_test_timing 測量。S2
  • 網路傳輸不計入；輸出轉換除非指定 SERIALIZE 選項否則也不計入。S2
  • LIMIT 可能讓節點提早停止，估計值仍顯示完整執行的數字，所以實際列數與時間可能低於估計值——這不是估計錯誤。S2
  • BitmapAnd 與 BitmapOr 因實作限制，實際列數一律回報為 0。S2

type 由好到壞

system → const → eq_ref → ref → fulltext → ref_or_null → index_merge → unique_subquery → index_subquery → range → index → ALL。S10 - const：最多一列符合，查詢開始時讀一次，通常是對 PRIMARY KEY 或 UNIQUE 索引全部欄位用常數查找。S10 - eq_ref：對先前表的每組列回傳一列，PRIMARY KEY 或 UNIQUE NOT NULL 索引的所有部分都以 = 比對。除 system 與 const 外最好的連接型別。S10 - range：以 =、<>、>、BETWEEN、IN、LIKE、IS NULL 等運算子做索引範圍掃描。S10 - index：掃描整棵索引樹。若索引覆蓋查詢，這是 index-only scan，通常比 ALL 快；否則依索引順序讀取資料列。S10 - ALL：全表掃描。通常是最差的型別。S10

常見 Extra 值

  • Using index：完全由索引回答，不讀表列（覆蓋索引），一般是好事。S10
  • Using where：讀出列後再套用 WHERE 條件過濾。若 type 是 ALL 或 index 而這個值沒出現，查詢可能讀了遠超過必要的列數。S10
  • Using filesort：沒有索引能提供所需順序，需額外一輪排序。大結果集時值得設法減少。S10
  • Using temporary：需要暫存表存放中間結果，常見於 GROUP BY 與 ORDER BY 列出的欄位不同時。S10

C5 — 常見反模式9 處引註

來源：S1, S4, S5, S6, S8, S9, S10, S11, S14 適用範圍：通用

1. 在 LEFT JOIN 之後用 WHERE 過濾右表

把條件放在 WHERE（連接之後）而非 ON（連接之前），會把未配對的列連同 NULL 一起濾掉，使外連接退化為內連接。S6

-- 保留未配對列（3 列）
SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num AND t2.value = 'xxx';
-- 濾掉未配對列（1 列）
SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num WHERE t2.value = 'xxx';

內連接時兩者等價，外連接時不等價。S6

2. 用 = NULL 檢查空值

expression = NULL 永遠回傳 null，不會配對到任何列。必須用 IS NULL。S5

3. 比較不同型別的欄位

MySQL：比較不同型別（例如字串欄位對數值欄位）可能導致索引無法使用。連接欄位宣告為相同型別與大小時索引效率最好，非二進位字串欄位還需使用相同字元集。S8

4. 用函數包住被索引的欄位

見 B4。WHERE UPPER(col) = 'X' 使欄位上的普通索引無法使用。S14

5. 前綴通配的 LIKE

見 B4。col LIKE '%bar' 無法使用 B-tree 索引。S1

6. SELECT * 使覆蓋索引失效

index-only scan 要求查詢只參照索引中儲存的欄位。SELECT x, z 在索引只含 (x, y) 時無法使用 index-only scan。S4 → 因此 SELECT * 幾乎必然要回表。

7. 盲目加索引

見 B6。多餘索引浪費空間、增加最佳化器負擔、拖慢所有寫入。S9

8. SQLite：OR 條件未必能用多索引

只有在 (1) 無法改寫成 IN，且 (2) 每一個 OR 子項都可各自索引化時，SQLite 才會考慮多索引聯集。即使適用，規劃器也可能因 OR 項過多或索引選擇性差而改選全表掃描。S11
