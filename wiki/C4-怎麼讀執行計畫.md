# C4 — 怎麼讀執行計畫

**來源**：S2, S10, S11
**適用範圍**：三引擎輸出格式完全不同（見 D2）

## PostgreSQL：EXPLAIN 與 EXPLAIN ANALYZE

- `EXPLAIN` 只顯示規劃器的**估計值**，查詢不會被執行。[S2]
- `EXPLAIN ANALYZE` **實際執行查詢**，在估計值旁加上每個節點的實際列數與執行時間，例如 `(actual time=0.017..0.051 rows=10.00 loops=1)`。[S2]
  - 實際時間單位是**毫秒**；成本是任意單位，兩者不可直接比較。[S2]
  - 節點執行多次（`loops > 1`）時，`actual` 的時間與列數是**每次執行的平均值**，乘上 `loops` 才是總量。[S2]
  - 因為查詢真的被執行，副作用會發生。要分析 DML 應包在 `BEGIN; ... ROLLBACK;` 中。[S2]
  - `ANALYZE` 會隱含啟用 `BUFFERS`。[S2]

### 三種掃描節點

| 節點 | 行為 | 何時被選中 |
|---|---|---|
| **Seq Scan** | 依實體順序讀過表的每一列，條件以 `Filter:` 套用 | 需要表中很大一部分時 [S2] |
| **Index Scan** | 走訪索引，依索引順序逐筆取出對應的表列。每次取用都是隨機存取，每列成本高 | 回傳極少列，或 `ORDER BY` 與索引順序相符時 [S2] |
| **Bitmap Heap Scan** | 兩段式，通常位於 `Bitmap Index Scan` 之上。後者從索引收集符合列的位置成為 bitmap，前者把這些位置**排成實體順序**再取列，藉此避開大部分隨機存取成本，並以 `Recheck Cond:` 重新檢查條件 | 中等選擇性：多於少數幾列但遠少於整張表時 [S2] |

官方範例：[S2]
```
EXPLAIN SELECT * FROM tenk1 WHERE unique1 = 42;
 Index Scan using tenk1_unique1 on tenk1  (cost=0.29..8.30 rows=1 width=244)
   Index Cond: (unique1 = 42)

EXPLAIN SELECT * FROM tenk1 WHERE unique1 < 100;
 Bitmap Heap Scan on tenk1  (cost=5.06..224.98 rows=100 width=244)
   Recheck Cond: (unique1 < 100)
   ->  Bitmap Index Scan on tenk1_unique1  (cost=0.00..5.04 rows=100 width=0)
         Index Cond: (unique1 < 100)
```

### 判讀的注意事項

- 計時儀器本身有開銷，在 `gettimeofday()` 較慢的系統上可能很顯著，可用 `pg_test_timing` 測量。[S2]
- 網路傳輸**不計入**；輸出轉換除非指定 `SERIALIZE` 選項否則也不計入。[S2]
- `LIMIT` 可能讓節點提早停止，估計值仍顯示完整執行的數字，所以實際列數與時間可能低於估計值——**這不是估計錯誤**。[S2]
- `BitmapAnd` 與 `BitmapOr` 因實作限制，實際列數一律回報為 0。[S2]

## MySQL：EXPLAIN 輸出欄位

| 欄位 | 意義 |
|---|---|
| `id` | 查詢中 SELECT 的序號 |
| `select_type` | SELECT 的種類（SIMPLE、PRIMARY、UNION、SUBQUERY、DERIVED、MATERIALIZED 等）|
| `type` | 存取方法，見下 |
| `possible_keys` | 最佳化器可能考慮的索引；NULL 表示無相關索引 |
| `key` | 實際選用的索引；NULL 表示未使用索引 |
| `key_len` | 使用的鍵部分長度（位元組），可看出**複合索引用到了多少欄** |
| `rows` | 預期檢查的列數估計 |
| `filtered` | 通過條件後剩餘的百分比估計 |
| `Extra` | 額外細節 |
[S10]

### `type` 由好到壞

`system` → `const` → `eq_ref` → `ref` → `fulltext` → `ref_or_null` → `index_merge` → `unique_subquery` → `index_subquery` → `range` → `index` → `ALL`。[S10]
- `const`：最多一列符合，查詢開始時讀一次，通常是對 PRIMARY KEY 或 UNIQUE 索引全部欄位用常數查找。[S10]
- `eq_ref`：對先前表的每組列回傳一列，PRIMARY KEY 或 UNIQUE NOT NULL 索引的所有部分都以 `=` 比對。除 `system` 與 `const` 外最好的連接型別。[S10]
- `range`：以 `=`、`<>`、`>`、`BETWEEN`、`IN`、`LIKE`、`IS NULL` 等運算子做索引範圍掃描。[S10]
- `index`：掃描整棵索引樹。若索引覆蓋查詢，這是 index-only scan，通常比 `ALL` 快；否則依索引順序讀取資料列。[S10]
- `ALL`：全表掃描。通常是最差的型別。[S10]

### 常見 `Extra` 值

- **Using index**：完全由索引回答，不讀表列（覆蓋索引），一般是好事。[S10]
- **Using where**：讀出列後再套用 WHERE 條件過濾。**若 `type` 是 `ALL` 或 `index` 而這個值沒出現，查詢可能讀了遠超過必要的列數。**[S10]
- **Using filesort**：沒有索引能提供所需順序，需額外一輪排序。大結果集時值得設法減少。[S10]
- **Using temporary**：需要暫存表存放中間結果，常見於 GROUP BY 與 ORDER BY 列出的欄位不同時。[S10]

## SQLite

前綴 `EXPLAIN QUERY PLAN` 可得到「所選查詢策略的高階概觀」。開發者用它確認是否使用了 OR 子句最佳化、索引或全表掃描。[S11]
