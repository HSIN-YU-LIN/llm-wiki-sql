# B4 — 索引失效的典型情境

**來源**：S1, S14, S11, S8
**適用範圍**：各引擎皆有，但條件細節不同（見 D1）

## 1. 前綴通配：`LIKE '%bar'`

**PostgreSQL 18**：B-tree 索引只有在模式是**常數**且**錨定於字串開頭**時才可用於 `LIKE` 與 `~`。[S1]
- 可用：`col LIKE 'foo%'`、`col ~ '^foo'`
- **不可用：`col LIKE '%bar'`**
- 地區設定但書：若資料庫未使用 C locale，索引必須以特殊的 operator class 建立才能支援模式比對查詢。[S1]
- `ILIKE` 與 `~*` 只有在模式以**非字母字元**（不受大小寫轉換影響的字元）開頭時才能用索引。[S1]

**SQLite** 的條件更細（LIKE/GLOB optimization 必須**全部**滿足）：[S11]
1. 右側是字串常值（或綁定到字串常值的參數），且**不以通配字元開頭**
2. 數值型的左運算元不得使 運算子為真。或者 (a) 左運算元是具 **TEXT affinity** 的索引欄位，或 (b) 模式不以 `-` 或數字開頭
   - 文件給的理由：`9<10` 但 `'9'>'10'`——數字不按字典序排列
3. 內建 LIKE/GLOB 函數未被 `sqlite3_create_function()` 覆寫
4. GLOB：欄位須使用內建 **BINARY** collation
5. LIKE：`case_sensitive_like` 為 ON 時欄位須用 BINARY，為 OFF（預設）時須用 **NOCASE**。只有這兩種組合可最佳化
6. 若用 `ESCAPE`，跳脫字元須為 ASCII 或單位元組 UTF-8

**機制**：對非通配前綴 *x*，令 *y* 為同長度中最小的、比較大於 *x* 的字串（例：`'hello'` → `'hellp'`），SQLite 加入兩個虛擬條件 `column >= x AND column < y`。原本的 LIKE 通常仍逐列檢查；只有在模式恰為 `column LIKE x%`（單一尾端通配）時才會省略。[S11]

## 2. 函數包裹欄位：`WHERE UPPER(col) = ...`

- 對索引欄位套用函數會使資料庫無法使用該欄位上的**普通索引**。[S14]
- 例：`LAST_NAME` 上的索引，只在搜尋時大小寫與儲存值一致才有用；為了大小寫不敏感而用 `UPPER` / `LOWER` 包住欄位，就是問題所在。[S14]
- **補救方式**：[S14]
  - **函數式 / 運算式索引**：PostgreSQL（7.4 起）、Oracle（8i 起）、Db2 LUW（10.5 起，不允許使用者自訂函數）
  - **計算欄位 / 生成欄位**：SQL Server 2000 起支援索引化計算欄位；MySQL 5.7 起支援生成欄位上的索引
  - 以上皆不可得時：新增一個實體欄位存放函數結果，用觸發器或應用程式維護，對它建索引，並把 `WHERE` 改寫成針對該欄位、不含運算式

> ⚠ 寫稿注意：S14 的頁面**未說明**資料庫在索引失效後改用什麼計畫（是否為全表掃描），也**未提供**日期函數的例子。不可憑推測補上。

## 3. 型別不一致

MySQL：連接欄位的型別與大小相同時索引效率最好；**比較不同型別（例如字串欄位對數值）可能導致索引無法使用**。[S8]

## 4. 前導欄位未約束

見 B3。SQLite 範例 `WHERE b IN (1,2,3) AND c NOT NULL AND d='hello'`（索引 `(a,b,c,d)`）→ a 未約束，索引不可用，全表掃描。[S11]

## 5. SQLite 的 unary `+`

`+x=5` 中的一元 `+` 會使該條件無法約束索引。文件警告這是最後手段的繞道方式，且會移除 affinity，可能改變比較語意。[S11]
