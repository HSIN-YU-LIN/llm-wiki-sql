# C2 — JOIN 演算法

**來源**：S16, S11, S10, S2
**適用範圍**：PostgreSQL 18 為主；各引擎支援度不同（見 D1）

## PostgreSQL 的三種連接策略

**1. Nested loop join（巢狀迴圈連接）**[S16]
- 對左側關聯的**每一列**，把右側關聯掃過一次。
- 文件評價：容易實作，但**可能非常慢**。
- 何時是好選擇：**右側關聯可用索引掃描存取時**——因為目前這一列左側的值可以直接當作索引鍵。

**2. Merge join（合併連接）**[S16]
- 兩個關聯都先**依連接屬性排序**，然後平行掃描並合併相符的列。
- 文件評價：吸引人之處在於**每個關聯只掃描一次**。
- 排序可以是明確的排序步驟，也可以來自用連接鍵上的索引以正確順序掃描關聯。

**3. Hash join（雜湊連接）**[S16]
- 先掃描右側關聯，以其連接屬性為鍵**載入雜湊表**。
- 再掃描左側關聯，用每一列的連接值去**探測（probe）**雜湊表尋找相符項。

> ⚠ 文件**未給出**何時 hash join 或 merge join 優於其他策略的明確指引。唯二明述的優勢是 nested loop 的索引情境與 merge join 的單次掃描。[S16]

## 連接順序的搜尋

- 超過兩個關聯的查詢，結果建成**二元連接步驟的樹**，規劃器評估不同的連接序列找出最便宜者。[S16]
- 關聯數少於 `geqo_threshold` 時，規劃器進行**近乎窮舉**的搜尋。[S16]
- 它偏好連接那些在 `WHERE` 條件中有連接子句的關聯對；沒有連接子句的配對只在某個關聯別無選擇時才考慮。[S16]
- 超過 `geqo_threshold` 時改用啟發式方法，即**基因查詢最佳化器（GEQO）**。原因是窮舉在連接數多時會耗費過多時間與記憶體。[S16]
- 搜尋在輕量的「路徑（path）」上進行，找到最便宜的路徑後才建出完整計畫樹交給執行器。[S16]

## 其他引擎

- **SQLite 把所有連接都實作為巢狀迴圈**，沒有 hash join 或 merge join。預設最左的 FROM 表為外層迴圈，規劃器可重排迴圈以取得更好的索引；內連接可自由重排，外連接不可（不具交換律與結合律），`CROSS JOIN` 永不重排。[S11]
  - 官方範例顯示同一查詢的兩種巢狀順序在特定資料分布下差異可達**約 2000 倍**。[S11]
- **MySQL**：`EXPLAIN` 的 `Extra` 顯示 **Using join buffer** 時，代表使用了 Block Nested Loop、Batched Key Access 或 hash join。[S10]
- **PostgreSQL 的判讀陷阱**：merge join 在外層鍵重複時會重掃內層列，`EXPLAIN ANALYZE` 把這些重複計為額外的列，可能使內層子節點回報的列數膨脹。[S2]

## 教學重點

同一個 JOIN，資料庫有三種完全不同的執行方式，成本差異可以是數量級的。而**選哪一種由最佳化器根據統計估計決定**，不是由你寫的 SQL 決定——這回扣 A2 的宣告式特性。
