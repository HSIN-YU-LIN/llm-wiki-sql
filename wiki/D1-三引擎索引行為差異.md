# D1 — 三引擎的索引行為差異

**來源**：S1, S2, S3, S4, S8, S10, S11
**⚠ 版本相依條目：任何引用本條目的陳述，都必須標明引擎與版本。**

| 項目 | PostgreSQL 18 | MySQL 8.0 | SQLite |
|---|---|---|---|
| 預設索引型別 | B-tree（`CREATE INDEX` 未指定 `USING` 時）[S1] | 多數索引以 B-tree 儲存 [S8] | （本次來源未明述；S11 討論的是規劃器而非索引型別）|
| 其他索引型別 | Hash、GiST、SP-GiST、GIN、BRIN，加 `bloom` 擴充 [S1] | 空間型別用 R-tree；MEMORY 表支援 hash；InnoDB 的 FULLTEXT 用倒排串列 [S8] | 未涵蓋 |
| 複合索引上限 | 32 欄（含 `INCLUDE`）[S3] | 本次來源未提供 | 本次來源未提供 |
| 複合索引官方態度 | **節制使用**；多數情況單欄索引足夠；超過三欄除非使用方式極固定否則不太可能有幫助 [S3] | 建議建立少量串接索引而非大量單欄索引 [S8 相關章節] | 規則以「前綴不可有缺口」陳述 [S11] |
| 前導欄位未約束時 | 可能使用 **skip scan**（為前導欄位的每個可能值動態產生等值條件），但通常只在前導欄位相異值很少時才選用；相異值多時規劃器通常改選全表掃描 [S3] | 僅支援最左前綴查找 [S8] | 不允許缺口；a 未約束則索引不可用（skip-scan 為例外）[S11] |
| LIKE 可用索引的條件 | 模式須為常數且錨定開頭；非 C locale 須用特殊 operator class [S1] | 本次來源未提供精確條件 | 六項條件全部滿足才可（含 collation、affinity、是否覆寫函數）[S11] |
| 連接演算法 | 文件提及 merge join、nested loop [S2] | Block Nested Loop / BKA / hash join（由 Extra 得知）[S10] | **只用 nested loop**[S11] |
| 覆蓋索引語法 | `INCLUDE`（僅 B-tree、GiST、SP-GiST 支援）[S4] | 查詢只需索引內欄位時自動生效，`Extra` 顯示 Using index [S8][S10] | 本次來源未提供 |

## 本條目的使用規則

1. 表格中標為「本次來源未提供」者，**不得在簡報中補上任何內容**，即使模型認為自己知道。
2. 任何跨引擎的概括性陳述（「所有資料庫都…」）必須退回為「PostgreSQL 18 的文件說…」。
3. 在 sqlite3 上實跑驗證的結果，**只能證明 SQLite 的行為**，不可當作 PostgreSQL 或 MySQL 的證據。
