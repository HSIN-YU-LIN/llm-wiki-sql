# C5 — 常見反模式

**來源**：S1, S4, S5, S6, S8, S9, S10, S11, S14
**適用範圍**：通用

## 1. 在 LEFT JOIN 之後用 WHERE 過濾右表

把條件放在 `WHERE`（連接之後）而非 `ON`（連接之前），會把未配對的列連同 NULL 一起濾掉，使外連接退化為內連接。[S6]
```sql
-- 保留未配對列（3 列）
SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num AND t2.value = 'xxx';
-- 濾掉未配對列（1 列）
SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num WHERE t2.value = 'xxx';
```
內連接時兩者等價，外連接時不等價。[S6]

## 2. 用 `= NULL` 檢查空值

`expression = NULL` 永遠回傳 null，不會配對到任何列。必須用 `IS NULL`。[S5]

## 3. 比較不同型別的欄位

MySQL：比較不同型別（例如字串欄位對數值欄位）**可能導致索引無法使用**。連接欄位宣告為相同型別與大小時索引效率最好，非二進位字串欄位還需使用相同字元集。[S8]

## 4. 用函數包住被索引的欄位

見 B4。`WHERE UPPER(col) = 'X'` 使欄位上的普通索引無法使用。[S14]

## 5. 前綴通配的 LIKE

見 B4。`col LIKE '%bar'` 無法使用 B-tree 索引。[S1]

## 6. `SELECT *` 使覆蓋索引失效

index-only scan 要求**查詢只參照索引中儲存的欄位**。`SELECT x, z` 在索引只含 `(x, y)` 時無法使用 index-only scan。[S4]
→ 因此 `SELECT *` 幾乎必然要回表。

## 7. 盲目加索引

見 B6。多餘索引浪費空間、增加最佳化器負擔、拖慢所有寫入。[S9]

## 8. SQLite：OR 條件未必能用多索引

只有在 (1) 無法改寫成 `IN`，且 (2) **每一個** OR 子項都可各自索引化時，SQLite 才會考慮多索引聯集。即使適用，規劃器也可能因 OR 項過多或索引選擇性差而改選全表掃描。[S11]
